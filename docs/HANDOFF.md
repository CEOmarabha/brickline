## The business in five lines

- Founder: khaled, Chicago-based, building mostly with AI tools, no existing industry contacts, a few thousand dollars of budget, wants real cash flow within a year.
- Product: **Brickline**, lead intelligence for Chicago contractors built on public records. Every lead shows evidence, a historical "chance of work", an expected value, and a drafted letter or email.
- Go-to-market: **Track 1 (cash flow)**: owner-facing trades (start with porch and masonry) get weekly trigger lists plus done-for-you mail; khaled runs pilots himself from client workspaces. **Track 2 (software asset)**: commercial subcontractor intelligence (GC "open door" scores, pre-application project predictions).

## Python essentials

- `uv` at `~/.local/bin/uv` (`export PATH="$HOME/.local/bin:$PATH"`). Run modules from the repo root: `uv run python -m engine.leads.snapshot`.
- Lint: `uv run ruff check engine research && uv run ruff format engine research` (SQL-heavy modules are exempt from E501 in `pyproject.toml`).
- DuckDB quirks: lambdas use `lambda x: ...`; `QUALIFY` can't combine with `GROUP BY ALL`; break ties explicitly (`ORDER BY ..., id`) so results are deterministic; use `first(x ORDER BY ...)` over `arg_max` when ties matter.
- Verify determinism after changing research code: run twice and compare `md5sum` of the findings file. Also run once under a low memory limit (e.g. wrap `duckdb.connect` so `memory_limit` is 1 GB): row order can change when DuckDB spills to disk, so an unbroken sort tie gives a different file only under memory pressure (that is how the duplicate investor lead id was found).
- DuckDB 2.0.0 (pinned in `uv.lock`, the latest stable) raises an internal "dict-surviving cache" assertion in the snapshot's 311 query when run with `SET threads = 2`. The default thread count (4 on the cloud VM), 1 and 8 work and give identical output; don't set threads to 2.

## Data facts that bite

- Chicago permits publish **only issued** permits; trade subcontractors are already named on most big permits at issue.
- Cook County sales lag ~3 months; the parcel tax roll lags sales (owner/mailing may still be the seller; `same_entity` handles this in the snapshot).
- Only ~50% of pre-2024 permits carry a PIN; `prepare_base` fills parcels from addresses.
- Permits undercount real work (windows, HVAC swaps, small repairs are often unpermitted): every rate is a floor.
- Overture releases rename columns (2026-10 has `taxonomy`, older ones `categories`; `engine/collect/overture.py` handles both). Overture is CDLA-Permissive-2.0 and needs attribution (shown as "Overture Maps" beside each suggestion; text in `docs/data-source-registry.md`). The Chicago bbox also contains western suburbs (Oak Brook), so `places.in_chicago` also requires locality Chicago or a 606xx ZIP.
- Permit contractor names are cut at 30 characters; `engine/enrich/contacts.py` has a prefix-match rule for them. Contact matching is name-only and deliberately conservative (match rates in `research/findings/contact-enrichment-<date>.md`).
- Community areas for leads come from point-in-polygon (DuckDB `spatial` extension, installed at runtime).
- The food-inspection pest flag (`f_pest`) is loose: in the last 52 weeks 37% of fresh pest findings mention only the generic word "pests" (usually entry points or clutter, not a sighting). The pest pilot list marks them "general mention only". Inspections post with a lag: the newest week can have a quarter of a normal week's inspections, so the "this week" pest list grows on later refreshes.
- Food inspections have no full street address or ZIP in the warehouse, only `address_key`; Cook County condo units share a `pin10` (a sale-level `pin` is 14 digits).
